## S4. 보드 벤치: 출발 구간 입력 (11:42~12:06)

**미리 정한 판정 문장 "119개 녹화의 출발 구간 모든 응답에서 보드 풀이 시간 최대가 29 ms 이하다": 참.**

| 항목 | 결과 |
|---|---|
| 표본 | SILS 녹화 119개 전부, 출발 구간 요청 63,360개, 운영 설정 SQP 2·QP 16 (보드 설정 확인 OK) |
| 응답 누락·링크 오류 | 0 |
| 보드 풀이 시간 | 최대 **28.28 ms**, p99.9 23.42 ms, p99 18.97 ms. 28.5 ms(기존 벤치 최대) 초과 0, 29 ms 초과 0 |
| 최악 지점 | 마지막 비정상 요청 7개 전, 차속 1.04 m/s, 반복 상한(SQP 2 × QP 16 = 32회) 도달 |
| 출발 순간(마지막 비정상 요청 뒤 0~5개) 최대 | 26.57 ms |
| 응답 처리 시간(total_us) 최대 / 왕복 최대 | 28.39 ms / 37.99 ms |
| status | 정상 61,633, QP 상한 1,719, **NUMERIC 8** |

해석(판정 아님):
- 장시간 시험의 30.7 ms 는 **재현되지 않았다.** 그 요청은 HILS 기록에 남지 않아 같은 입력을 넣을 수 없었다(계획에 먼저 적은 제약). 같은 종류의 입력 63,360개에서는 29 ms 를 넘지 않았다. **재현되지 않은 이유는 확인하지 못했다**(정정 2026-11-12: 처음 판은 "녹화에 없는 더 드문 입력"이라고 단정했다). 입력 차이일 수도 있고, HILS 폐루프의 warm start 이력 차이나 풀이 중 인터럽트 부하(HILS 에서는 안전 제어기용 차량 CAN 프레임이 함께 들어온다)일 수도 있다. 30.7 ms 때 반복 횟수는 이미 상한(32회)이었으므로, 반복 상한이 시간 상한을 만들지 못한 사례다(미해결 DEF-31 과 같은 내용). 계산 시간이 "측정 최대이며 WCET 증명이 아니다"라는 기존 한계는 그대로다.
- NUMERIC 8건은 모두 마지막 비정상 요청(c0 ≈ 10¹², 실제 경로가 아님) 자체에서 나왔고 6 ms 안에 오류로 끝났다. 장시간 시험의 출발 순간 풀이 오류 2건과 같은 모습이며, 입력이 비정상이라 생긴 것으로 본다(DEF-38 과 같은 지점).
- 풀이 시간 0 ms 응답 384개는 모두 녹화 첫머리의 정차 요청(차속 0, 반복 0회, 정상 status)으로, 풀이를 하지 않은 주기다. 그림 `poster/img/g_startup_bench.png`.
- 도구 `startup_bench.cpp` (md5 `tool.md5`)는 호스트 도구이며 펌웨어는 바꾸지 않았다. 설정은 브리지 yaml + SQP/QP 만 바꿨다(TC-B01 과 같은 방식). 각 녹화는 처음부터 보내 warm start 가 실제 주행처럼 이어진다. 다만 녹화는 SILS 설정(S3·Q200)으로 달린 랩이라, 보드(S2·Q16)가 낸 명령과 그 뒤 입력의 피드백은 원래 주행과 다르다.
