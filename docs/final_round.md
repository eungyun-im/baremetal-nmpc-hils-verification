# Final round (2026-11-11 to 2026-11-12)

This page summarizes the last verification round and the corrections made to its report. Raw records, most of them in Korean, are in [`verification/final_round/`](../verification/final_round).

- No MISRA, ASPICE or ISO 26262 compliance is claimed.
- The vehicle is a simulator (MORAI K-City). Perception, localization and path planning stay on the PC; the MCU runs the MPC solve and the safety controller.
- The firmware that ran is a bench build with the fault-injection hook. A release-configuration build was not run on the board.
- Measured execution times are not a WCET bound.

## What was fixed before measuring

Sixteen requirements (4 functional, 5 non-functional, 7 safety) with their criteria, test cases and lap counts were written in the specification v0.3 before the first official lap (`verification/final_round/spec_ko/req_test_spec.md`). The lap plan was 89 laps: 20 each for the MCU (HILS), the same C code on the PC (SILS) and the original PC controller (CppAD + Ipopt), in interleaved blocks of five, plus 29 fault laps (`plans/laps_plan_final3.json`).

What "fixed before measuring" does and does not cover:

- It holds for the driving-lap tests. Some criteria (for example the 50 ms control-cycle limit) had been set after looking at 93 earlier laps, and the bench, replay, PIL and host tests already had results when v0.3 was written.
- During the round, at about 40 valid laps, two definitions were changed at the author's request (v0.4). They were reverted, and the official verdict uses v0.3. The v0.4 analysis is kept as a supplement only.
- The repository that holds the specification is not under version control, so the only independent evidence of the timing is the lap plan's checksum and modification time (14:54, first official lap 15:09).
- The verdict script was still edited after the laps ended. One of those edits was the bug described under [Corrections](#corrections).

How to read "pass":

- **NFR-02 does not show a bound.** It says the solve stayed under 29 ms in the samples fixed in advance. With the same firmware, a 2.9 h soak later produced one 30.7 ms solve, at the iteration cap. The firmware has no solve deadline handling (open defect, see below).
- **NFR-01 is a 20-lap result.** In the 57-lap soak, 5 laps violated one of its items. If that rate applies, the chance of 20 clean laps is about 16 %.
- **"No safe stop" tests need evidence that the fault went in.** For the request-CRC and short solver-failure tests the MCU response shows the error status; for the vehicle-CRC test there is only the bridge's injection log.
- **Reaction times are the time the safe state is entered**, read from a log with about 50 ms resolution. The safe stop holds the last steering angle; whether the vehicle then stays in its lane is not judged.
- **Collisions and lap completion are not among the 16 requirements.** See [Collision flags](#collision-flags).

## The two failures

**FR-01, maximum path error.** All 8 HILS laps exceeded in the M3 restart section, where the reference path moves 1-2 m while the car is still on the previous path (21 of 22 M3 events across the three configurations). The same happens at a similar rate in SILS and with the original controller, so it is not specific to the MCU port. The mechanism is known (the reference returns to the centreline at the section boundary), the causality is not confirmed. One official SILS event is not explained by a reference change, and neither are 8 of the 21 soak-lap exceedances. The 2.29 m maximum is a different event: one HILS lap, after the tunnel exit, with the localization several metres off inside the tunnel; cause not confirmed.

**FR-03, board vs PC.** The 0.01° criterion is strict for float code built by two compilers, but it was not changed after the result was seen. FMA contraction on the board explains part of the difference; the rest is unconfirmed. A separate effect appears right after the start (see defect DEF-38).

## Delay

| | Pose-to-command delay, mean |
|---|---|
| HILS (MCU) | 41.4 ms |
| Original controller (PC, Ipopt) | 28.7 ms |
| SILS (same C code on the PC) | 10.8 ms |

The HILS delay split by segment, over 75,467 cycles of the 20 official laps, each cycle matched across topics (analysis after the verdict, `robustness/latency_split.py`):

| Segment | Mean | How obtained |
|---|---|---|
| Pose age when the request is filled | 10.1 ms | measured |
| Other PC time | 3.3 ms | remainder: control cycle − round trip − safety wait |
| Transfer segment | 9.6 ms | remainder: round trip − MCU processing. Includes CAN wire time, USB serial, kernel and the bridge's 1 ms gap between request frames |
| MCU processing (solve 13.4 ms) | 13.5 ms | measured on the board |
| Wait for the safety controller's checked output | 4.9 ms | measured; about half of the 10 ms safety period |
| Sum | 41.4 ms | |

Subtracting the transfer segment gives 31.8 ms, and subtracting the safety wait as well gives 26.9 ms, a little below the original controller's 28.7 ms. These are subtractions of means, not measurements of such a configuration. How much of the 9.6 ms is CAN wire time (about 2.5 ms by calculation for 10 frames at 500 kbps) was not measured.

**Control cycle time while driving is similar in both configurations.** Maximum 61.7 ms for the original controller and 48.7 ms for the MCU configuration (57.4 ms in the soak); p99 29.6 ms and 37.4 ms. The clear difference is before the start, on abnormal requests: about 150 ms per cycle for the original controller against at most 45 ms for the MCU configuration. The table value "163.1 ms maximum" for the original controller is such a pre-start cycle caught as the first sample of the judged window in 8 of 20 laps.

Tracking stayed within lap-to-lap spread of the original despite the longer delay (the MCU side is 9-12 % higher in mean path error and lateral RMS). The contribution of delay compensation is shown only by SILS delay-injection runs and by HILS runs on earlier firmware; no compensation-off control run was made on the final firmware.

## Collision flags

The simulator's collision topic was scanned in all 210 valid laps (official and confirmation 109, soak 57, supplementary 44). Five laps contain messages with another vehicle within 5 m of the ego centre:

- **Approach while driving, M6 merge section, 2 laps.** An official HILS fault lap (the request-CRC lap used for SR-07): another vehicle within 5 m for 2.7 s, closest 1.9 m, 96 s after the injection, ego speed dropping from 14.5 to 3.2 m/s. The lap runner's own report marks this lap as a collision failure. A supplementary SILS lap: closest 2.2 m, ego speed dropping from 11.1 to 1.9 m/s. It happened in both HILS and SILS.
- **Ego stationary in M5 while other vehicles pile up nearby, 3 laps.** One official SILS lap and two soak HILS laps, closest 4.3-4.4 m, 3.0 s each.

Whether there was contact, and the cause (controller, planner or the other vehicle), was not determined. This is an open item.

## Assumptions behind the 290 ms limit

The limit is the time to leave the lane on the tightest curve of the course (radius about 11 m at 7 m/s), computed with an assumed lane width of 3.5 m. Measured from the map, the lane at that location is 3.30-3.35 m wide, which gives about 250-270 ms (225 ms with a pessimistic centre-of-gravity position). The one reaction measured at that location, a solver failure, was 208.7 ms. Bus-off has neither a time criterion nor a measurement: during the injection the PC adapter is at another bit rate and sees the state only after the bus returns (about 830 ms).

A hazard list written after the fact (`robustness/hara_posthoc.md`, not an ISO 26262 HARA) shows what the seven safety requirements do not cover: bus-off reaction time, a late command when a cycle overruns, abnormal input before the start, and unintended acceleration.

The main ones:

| What the report said | Correction |

| "Without CAN and the safety wait, the delay equals the original (26.7 vs 26.6)" | 26.9 vs 28.7 ms, and only as a subtraction of means |
| "The maximum cycle time fell from 163 ms to 28.5 ms" | Different quantities, and the 163 ms is a pre-start cycle. While driving: 61.7 ms and 48.7 ms |
| "Solve time has an upper bound" | Not shown. One 30.7 ms solve at the iteration cap; no deadline handling |
| "All seven faults reacted within 290 ms" | Time was measured for 4 fault types, 17 injections |
| "Bus-off safe stop takes 830 ms" | That is when the PC first saw the state; the MCU's time was not measured |
| "Reactions at the reference location were 205-209 ms" | One measurement there, 208.7 ms |
| "One official lap has collision messages" | Two, and the missing one was a HILS lap |
| "The 2.29 m maximum comes from the reference change" | It is a separate event after the tunnel exit |
| "The criteria were not changed after results were seen" | They were changed once and reverted |

No verdict changed in any correction.
